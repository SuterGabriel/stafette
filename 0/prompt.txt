1. Was ist Entire Brain?
Belegt: ein lokales CLI-Plugin mit optionaler MCP-Anbindung
Entire bezeichnet Brain im offiziellen Hackathon-Guide als „memory layer that lives in your repo, not in one agent“: Vorentscheidungen und Kontext sollen beispielsweise von Claude Code zu Codex mitgenommen werden können. Es wird als ausführbares Plugin entire-brain installiert und über entire brain … aufgerufen; zusätzlich ist eine MCP-Anbindung dokumentiert. Es ist damit nicht bloss eine Webfunktion oder ein eingebauter Befehl, der nach Installation der Basis-CLI automatisch verfügbar ist.

Der offizielle Installationsweg verwendet Bash:

bash
curl -fsSL https://raw.githubusercontent.com/entireio/entire-brain/main/scripts/get-brain.sh | bash
Danach im Projektverzeichnis:

bash
entire brain setup
entire brain init-agents
setup initialisiert den Repository-Kontext; init-agents bindet bestehende Sessions ein und erzeugt beziehungsweise aktualisiert .entire/agent-guide.md sowie verwaltete Verweise in AGENTS.md und CLAUDE.md. Danach die Agenten-Instruktionen neu laden beziehungsweise Claude Code neu starten.

Optional für Claude Code:

bash
entire brain mcp --print-config
claude mcp add entire-brain -- entire brain mcp
Die dokumentierte Nutzung erfolgt dann über den Coding-Agenten, der Brain für frühere Entscheidungen und Graph zur Code-Navigation verwendet. Ohne Graph bleiben laut Guide Sessions, Dokumente und Fakten nutzbar; ohne Entire CLI fehlen die erfassten Sessions und Brain greift auf Code, Dokumentation und Git-Historie zurück.

2. Was macht das offizielle Graph-Plugin?
Funktion und Installation
Graph analysiert lokalen Quellcode mit Tree-sitter und erstellt eine navigierbare Struktur aus Symbolen, Definitionen, Aufrufen, Typbeziehungen und Änderungsauswirkungen. Der eingebaute Analyzer arbeitet laut offiziellem Repository ohne Netzwerkzugriffe, Modellaufrufe oder API-Schlüssel; Graph ist kein autonomer Sicherheitsprüfer und kein vollständiger Beweis aller möglichen Laufzeitpfade.

Dokumentierte Voraussetzungen: Entire CLI ab 0.10.0 und Git ab 2.36 – eure Entire-Version 0.11.4 erfüllt somit die angegebene CLI-Mindestversion.

bash
entire plugin install graph
entire graph version
entire graph init-agents --repo .
Danach Claude Code neu starten beziehungsweise die Repository-Anweisungen neu laden.

Wichtige Inkonsistenz in den offiziellen Quellen
Der Hackathon-Guide spricht noch von .entire/graph-agent.md und dem ersten Agentenaufruf entire-graph search; das aktuelle Graph-README nennt .entire/agent-guide.md und verwendet entire graph query. Deshalb sind die Hilfe des tatsächlich installierten Plugins und dessen Version massgeblich, nicht eine aus verschiedenen Dokumentationsständen zusammengesetzte Syntax.

bash
entire graph help
entire graph query --help
Diese Vorgehensweise ist auch in der offiziellen Graph-Befehlsreferenz vorgesehen.

Exakte dokumentierte Beispiele
bash
entire graph query --profile full "route matching implementation for incoming request paths"
entire graph impact --symbol Router.Match
entire graph health --repo . --json
entire graph stats --repo .
query findet relevante Quellregionen, impact zeigt mögliche Auswirkungen einer Symboländerung, health Parser-/Indexierungsprobleme und stats die Nutzung des Graphs gegenüber grep/read in lokalen Agententranskripten. Die Tokenersparnis von stats ist ausdrücklich eine modellierte Schätzung, keine direkt gemessene Einsparung.

Offizieller Beispielausschnitt für impact, aus dem Graph-README:

text
Index: cache-hit (49ms) | Query: 0ms | Total: 50ms
Impact: Router.Match (mux.go:151) def=151 span=151-182 [method in Router]
Blast radius: 1 caller (1 direct, 0 transitive), 0 callees, 3 type consumers,
  1 data flow, 7 co-change files, 29 siblings.
Callers (1 direct, 0 transitive; who breaks if behavior changes):
- Router.ServeHTTP (mux.go:203, def :188)
Das ist eine historische Beispielausgabe, keine Laufzeitgarantie: Das README weist darauf hin, dass aktuelle Working-Tree-Abfragen standardmässig cache-miss melden und dass statische Analyse Aufrufe übersehen kann.

Zusammenhang mit Checkpoints
Graph erklärt die Struktur und Auswirkungen des Codes; Checkpoints speichern Coding-Session, Auftrag und Kontext hinter Änderungen. Graph unterstützt zusätzlich Commit- und Checkpoint-Analyse, aber für eine gewöhnliche lokale Codeabfrage müsst ihr nicht zuerst auf GitHub pushen oder einen Checkpoint erstellen.

7. Eure konkrete 20-Sekunden-Demo
Empfehlung: why → checkpoint explain
Bereitet einen kleinen, von Claude Code implementierten und getesteten Commit vor, beispielsweise mit dem Auftrag:

„Implementiere die deterministische Vollmachtsprüfung: unbekannte Aktion, abgelaufene Vollmacht oder nicht autorisierter Empfänger müssen blockiert werden. Ergänze Tests für diese Fälle.“

Aktiviert Entire vor dieser Coding-Session:

bash
entire enable --agent claude-code
Startet anschliessend eine neue Claude-Code-Session, lasst die Änderung implementieren und committet die tatsächlich geänderten Dateien. Ein normaler Checkpoint benötigt sowohl erfassten Agentenkontext als auch den Git-Commit.

Prüft vorher:

bash
entire checkpoint list
entire checkpoint explain HEAD --no-pager
Für die Bühne verwendet ihr zwei Befehle:

bash
entire why src/policy/authorize.ts:42
entire checkpoint explain HEAD --no-pager
Der Dateipfad und die Zeile sind bewusst Platzhalter für eure tatsächliche Prüfentscheidung; sie müssen vor der Demo ersetzt werden. HEAD muss der vorbereitete Policy-Commit sein, andernfalls verwendet dessen echte SHA oder Checkpoint-ID. Die Befehlssyntax ist offiziell dokumentiert.

Ablauf und Sprechtext
0–6 Sekunden: Euer eigener Agent schlägt eine nicht autorisierte Aktion vor; eure Anwendung zeigt die deterministische Ablehnung.

6–12 Sekunden: entire why an der Ablehnungszeile zeigt den ursprünglichen Sicherheitsauftrag und den Checkpoint.

12–20 Sekunden: entire checkpoint explain öffnet den gespeicherten Entwicklungsnachweis.

Sagt dazu:

„Der Agent schlägt diese Aktion vor, aber unsere Vollmachtsprüfung blockiert sie im Code. Mit Entire zeigen wir, aus welchem Auftrag diese Prüfung entstanden ist und welche Coding-Session die Implementierung dokumentiert. Die tatsächlichen Patientenaktionen protokollieren wir separat in unserem Laufzeit-Audit.“

Das ist meine Demoempfehlung, keine offizielle Juryanforderung. Der entscheidende Unterschied bleibt: Ein Checkpoint belegt gespeicherten Entwicklungskontext, aber weder automatisch die Korrektheit eurer Berechtigungslogik noch ein manipulationssicheres medizinisches Laufzeitprotokoll.
